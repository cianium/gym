# راهنمای نصب و تست امن — ARASH Fitness 2.3.2

## قبل از نصب

1. نسخه پشتیبان از `laravel_core/.env`، دیتابیس و فایل‌های خصوصی بگیرید و **کلیدهای `APP_KEY` و `BACKUP_ENCRYPTION_KEY` را حفظ کنید**. رمزها و کدها را در گفتگو یا گزارش عمومی قرار ندهید.
2. نسخه 2.3.2 را ابتدا روی دامنه آزمایشی و دیتابیس جداگانه از مشتریان نصب کنید؛ سرویس‌های بانکی واقعی را در تست روشن نکنید.
3. هاست به PHP 8.3+ و افزونه‌های ذکرشده در `composer.json` (از جمله `pdo_mysql`, `mbstring`, `gd`, `curl`, `xml`) نیاز دارد. Session و Cron باید فعال باشند.
4. `laravel_core` را بیرون از `public_html` قرار دهید؛ فایل‌های `public_html` داخل DocumentRoot دامنه باشند. `index.php` باید بتواند `../laravel_core` را پیدا کند.
5. مقدارهای `.env` نسخه قبلی را به‌آرامی حفظ کنید؛ هرگز روی سرور موجود بدون بررسی `.env` را با `.env.example` جایگزین نکنید. ویژگی جدید نیازی به migration اضافه ندارد اما migrationهای 2.3.1 باید قبلاً اعمال شده باشند.

## بررسی‌های اولیه بعد از نصب Staging

```bash
cd /path/to/laravel_core
php artisan optimize:clear
php artisan migrate:status
php artisan route:list --path=checkout
php tests/static_runtime_regressions.php
php tests/route_security_smoke.php
node tests/client_checkout_gate.mjs    # فقط در محیط توسعه با Node.js
```

اگر نسخه 2.3.1 migrationهای ناقص دارد، ابتدا **پس از بکاپ و بررسی دقیق** `php artisan migrate --force` را فقط روی Staging اجرا کنید.

## تست با دیتابیس موقت MySQL (هرگز روی دیتابیس سایت)

اسکریپت زیر شامل `DatabaseMigrations` است که جدول‌ها را پاک و از اول ایجاد می‌کند. بنابراین **فقط با دیتابیس جدید و کاملاً یک‌بارمصرف** اجرا کنید. به `pdo_mysql`, `pcntl`, PHPUnit توسعه و Composer نیاز دارید. در صورت نبود هرکدام، آزمون اجرا نخواهد شد.

```bash
cd /path/to/laravel_core
# روی ماشین توسعه، وابستگی‌های dev را نصب کنید:
# composer install
export APP_ENV=testing
export DB_CONNECTION=mysql
export DB_DATABASE=test_arash_fitness
export DB_HOST=127.0.0.1
export DB_USERNAME=your_disposable_test_user
# DB_PASSWORD را امن و خارج از تاریخچه شل تنظیم کنید.
export ARASH_ALLOW_DESTRUCTIVE_TESTS=YES_DISPOSABLE_DATABASE
bash tests/run_mysql_staging_suite.sh
```

اسکریپت قبل از اجرا نام دیتابیس را کنترل می‌کند و بدون متغیر تأیید خطر اجازه اجرا نمی‌دهد. روی هاست اصلی از آن استفاده نکنید.

## سناریوهای دستی اجباری قبل از انتشار

1. خریدار بدون ورود به `/checkout` برود: پنجره ثبت‌نام/ورود ظاهر شود؛ پرداخت واقعی شروع نشود؛ سه API عمومی 401 بدهند.
2. یک ورزشکار جدید ثبت‌نام کند: یک OTP دریافت کند؛ با کد غلط رد شود؛ با کد معتبر حساب و نشست ایجاد شود؛ بدون بارگذاری مجدد سایت امکان ادامه خرید وجود داشته باشد.
3. ورزشکار ثبت‌نام‌شده وارد شود: شماره سفارش متفاوت رد شود؛ شماره منطبق قبول شود؛ پس از خروج اجازه خرید از کاربر گرفته شود.
4. خرید همان سبد با همان کلید دو بار ارسال شود: فقط **یک سفارش و یک درخواست آغاز پرداخت** ایجاد شود. تغییر سبد با همان کلید باید 409 شود.
5. زرین‌پال GET و سامان POST را با پاسخ آزمایشی معتبر/نامعتبر/Timeout بررسی کنید؛ تکرار Callback نباید دوباره محصول دیجیتال تحویل دهد یا انبار کم کند.
6. دو ورزشکار هم‌زمان یک سانس مشاوره را انتخاب کنند: دقیقاً یک نفر موفق و نفر دوم 409؛ هیچ رزرو دوگانه ساخته نشود.
7. محصول فیزیکی با موجودی ۱، دو درخواست هم‌زمان: مجموع کالاهای رزروشده و فروخته‌شده از موجودی فراتر نرود.
8. نمایش پیامک ملی‌پیامک و صف اعلان برای مربی/ورزشکار با الگوی واقعی تأیید شود. پیام مبهم یا Timeout را خودکار «موفق» نشمارید.
9. کلید CSRF حذف یا اشتباه شود: همه مسیرهای Checkout باید 403 باشند. روی موبایل اندروید و دسکتاپ ثبت‌نام، modal، تایپ اعداد فارسی و بازگشت از درگاه تست شوند.
10. Snapshot رمزگذاری‌شده تهیه، بر یک دیتابیس قابل حذف Restore و با نسخه 2.3.1 تطبیق بررسی شود.

## معیار GO/NO-GO

تا وقتی تست‌های دیتابیس، درگاه، OTP و مرورگر واقعی موفق نشده‌اند، نتیجه **NO-GO برای Production** است. گذراندن بررسی نحوی و تست‌های بدون دیتابیس صرفاً مجوز استقرار Staging است.
