# ممیزی اولیه مخزن GitHub — ARASH Fitness 2.3.2

**تاریخ:** 2026-11-22  
**مخزن:** `cianium/gym`  
**شاخه:** `main`  
**نوع بررسی:** بررسی ساختار مخزن، اسناد، مسیرها و بازبینی ایستای بخش‌های حساس؛ بدون اجرای محیط Runtime

## ۱. تأیید مخزن

- مخزن خصوصی است.
- شاخه پیش‌فرض `main` است.
- ساختار اصلی `laravel_core/`، `public_html/` و `docs/` در GitHub موجود است.
- Stack اعلام‌شده با کد موجود هم‌خوان است: Laravel 13 / PHP 8.3+ / MySQL یا MariaDB.
- ۷ فایل Migration در مخزن وجود دارد؛ اجرای آن‌ها روی دیتابیس واقعی در این مرحله انجام نشده است.

## ۲. ناسازگاری مستندات که اصلاح شد

نسخه قبلی `docs/release/FINAL_QA_REPORT_FA.md` گزارش نسخه 2.2.0 بود و درباره کدهای Node/TypeScript، `server.ts`، Vite و تست Docker ادعاهایی داشت که به Snapshot فعلی Laravel 2.3.2 تعلق نداشت. این گزارش با نتایج مستند و قابل ردیابی نسخه 2.3.2 جایگزین شد.

سند `IMPLEMENTATION_STATUS_FA.md` نیز مربوط به 2026-11-09 بود و وضعیت OTP و قابلیت‌های بعدی را قدیمی نشان می‌داد؛ با وضعیت نسخه 2.3.2 به‌روزرسانی شد.

## ۳. یافته امنیتی و اصلاح انجام‌شده

### [HIGH] خروجی Backup به شکل plaintext

**شواهد کد پیش از اصلاح:**
- متد `SystemMaintenanceController::exportBackup()` فقط با پارامتر `encrypted=true` رمزگذاری می‌کرد.
- کلاینت اصلی مدیریت درخواست `/api/v1/admin/backup/export` را بدون پارامتر رمزگذاری ارسال می‌کرد.
- `buildBackupBundle()` داده‌های حساس را شامل می‌کند: فیلدهای احراز هویت کاربران، توکن دسترسی سفارش، تراکنش‌ها، اطلاعات سفارش و فایل‌های خصوصی.

**اصلاح انجام‌شده در main:**
- API اکنون همیشه `BackupVault::encryptBundle()` را اجرا می‌کند.
- نبود کلید معتبر باعث پاسخ 503 می‌شود؛ خروجی plaintext مجاز نیست.
- کلاینت مدیریت صریحاً `?encrypted=1` را درخواست می‌کند.
- URL باندل در `public_html/spa-shell.html` و `laravel_core/resources/views/spa.html` نسخه‌گذاری شده است.
- دو assertion جدید به `tests/static_runtime_regressions.php` اضافه شده است.

**اعتبارسنجی باز:** اجرای تست رگرسیون، تست دستی Export و Restore در Staging و بررسی سازگاری فایل خروجی با UI.

## ۴. یافته‌های فنی و محدودیت‌ها

1. سورس اصلی React/TypeScript ارائه نشده؛ فقط باندل‌های Build‌شده در `public_html/assets` موجود است. تغییرات بزرگ UI بدون بازیابی سورس، پرریسک و دشوار برای نگهداری است.
2. تست‌های Feature و MySQL concurrency در مخزن موجودند، اما وجود فایل تست به معنی اجرای موفق آن‌ها نیست.
3. اتصال واقعی MeliPayamak و درگاه بانکی با اعتبارنامه عملیاتی در این بررسی انجام نشده است.
4. Backup/Restore باید با دیتابیس و فضای فایل جداگانه آزمایش شود؛ کلید `BACKUP_ENCRYPTION_KEY` باید مستقل و خارج از Git نگهداری و برای Restore حفظ شود.
5. Callback شبیه‌ساز پرداخت در کد برای محیط `production` صریحاً غیرفعال شده است؛ این کنترل باید در تست Staging/Production نیز تأیید شود.
6. انتشار Production تا اجرای آزمون‌های دیتابیس، پرداخت، پیامک، Restore و مرورگر موبایل مجاز نیست.

## ۵. برنامه اجرایی بعدی

1. اجرای مجدد تست‌های مستقل از دیتابیس پس از اصلاح Backup.
2. اجرای `run_mysql_staging_suite.sh` فقط روی دیتابیس اختصاصی و قابل حذف با `APP_ENV=testing`.
3. اجرای Migrationها و Feature tests روی MySQL/MariaDB سازگار.
4. تست رزرو هم‌زمان، Checkout هم‌زمان و Callbackهای تکراری/دیرهنگام.
5. تست SMS outbox و تأیید رسیدهای واقعی MeliPayamak.
6. تست رمزگذاری Export، رمزگشایی و Restore کامل.
7. تست E2E موبایل/دسکتاپ و استقرار آزمایشی cPanel.

**نتیجه:** نسخه 2.3.2 برای ادامه توسعه و Staging مناسب است؛ هنوز Production-ready نیست.
