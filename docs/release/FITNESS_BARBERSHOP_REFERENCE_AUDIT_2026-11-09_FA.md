# ممیزی و سخت‌سازی پروژه مربی بدنسازی با الهام از الگوهای Barbershop

**تاریخ:** ۹ نوامبر ۲۰۲۶  
**مبنای بدنسازی:** `ARASH_PRODUCTION_RELEASE_2.2.0.zip`  
**مرجع مقایسه:** `Barbershop-Standalone-Latest-2026-11-09.zip`  
**وضعیت تحویل:** بسته اصلاح‌شده و قابل بررسی؛ **تأیید انتشار عملیاتی صادر نشده است**.

## اصل استقلال پروژه‌ها

- **بدنسازی** همچنان Laravel 13 + MySQL/MariaDB + `public_html` + `laravel_core` است.
- **Barbershop** همچنان Node/TypeScript + PostgreSQL/Supabase است و **هیچ فایل یا وابستگی از آن در بسته بدنسازی کپی نشده است**.
- تنها **الگوهای کنترل دسترسی، اعتبارسنجی اثبات پرداخت، نشست‌ها، idempotency، رویدادهای مالی و زمان‌بندی نگهداری** برای اصلاح کد Laravel استفاده شدند.

## اصلاحات واقعی در بسته تحویلی

| موضوع | ایراد واقعی مشاهده‌شده | اصلاح اعمال‌شده |
|---|---|---|
| Callback منفی بانکی | مسیر عمومی callback می‌توانست `State=NOK` را بدون تأیید سرور بانک به وضعیت `cancelled` تبدیل کند و رزرو موجودی را آزاد کند؛ در SEP فیلد Token روی این مسیر الزامی نبود. | callback منفی فقط نتیجه «تأییدنشده» می‌دهد؛ لغو و آزادسازی خودکار از مسیر کنترل‌شدهٔ انقضای سفارش انجام می‌شود؛ callback مثبت همچنان باید سرور به سرور بررسی شود. |
| رسید بانکی زرین‌پال | پاسخ موفق `code=100/101` بدون `ref_id` می‌توانست با شماره رهگیری محلی در کد callback جبران شود. | پرداخت بدون رسید بانکی به `verification_pending` می‌رود؛ callback نمی‌تواند شماره پیگیری ساختگی را به‌جای رسید ثبت کند. |
| ثبت دستی استرداد | سفارش پرداخت‌نشده می‌توانست `refunded` شود و در نبود شناسهٔ پیگیری، مقدار ساختگی `MANUAL-ADMIN` ثبت می‌شد. | پیش‌شرط وضعیت `paid` با قفل سطری و شناسه پیگیری بانکی اجباری اضافه شد؛ تحویل/نیاز به استرداد نیز فقط برای سفارش پرداخت‌شده مجاز است. |
| استعلام پس از استرداد | `retry_verify` در شرایطی می‌توانست سفارش مستردشده را دوباره پرداخت‌شده کند. | حالت `refunded` غیرقابل تغییر از مسیر استعلام مجدد شد؛ وضعیت `processing` از استعلام موازی محافظت می‌شود. |
| بازیابی تأیید بانک | امکان ماندن تراکنش `verified` در حالی که سفارش هنوز نهایی نشده، در صورت قطع فرایند بین این مراحل وجود داشت. | مدیر می‌تواند با رسید `verified` ذخیره‌شده، نهایی‌سازی سفارش را بازیابی کند، بدون اختراع پرداخت دوم. |
| Idempotency سبد | کلید یکسان برای یک تلفن و درگاه، بدون مقایسه محتوای درخواست، ممکن بود توکن مالکیت سفارش قبلی را بازگرداند؛ در زمان آغاز پرداخت نیز URL جایگزین ساختگی ساخته می‌شد. | مقایسه اقلام/مقادیر و اطلاعات مشتری در مسیر cache و دیتابیس، پاسخ `409` برای تعارض، کلید حداقل ۲۰ کاراکتری و پاسخ مشخص «آغاز تراکنش در جریان» اضافه شد. |
| دانلود برنامه دیجیتال | صرف تطبیق شماره تلفن حساب `athlete` با خریدار می‌توانست در توسعه آینده، بدون اثبات مالکیت شماره موبایل دسترسی بدهد. | احراز مالکیت از مسیر شماره تلفن تنها پس از احراز هویت و تأیید شماره مجاز است؛ تا زمان اضافه‌شدن OTP واقعی، توکن امن سفارش همچنان ضروری است. |
| رمز ادمین | تغییر رمز، سایر نشست‌های دیتابیسی را باطل نمی‌کرد و امکان ثبت ایمیل تکراری وجود داشت. | حداقل طول رمز جدید ۱۲ نویسه، کنترل یکتایی ایمیل، حذف سایر نشست‌های پایگاه داده و چرخش نشست جاری افزوده شد. |
| مشاوره | تولید شناسه با `time()+random_int(100..999)` مستعد برخورد در درخواست‌های هم‌زمان بود. | UUID مستقل و اعتبارسنجی فرمت شماره تماس جایگزین شد. |
| انقضای سفارش | آزادسازی موجودی سفارش رهاشده فقط هنگام checkout جدید اجرا می‌شد؛ در ساعات بدون خرید، سفارش‌ها معلق می‌ماندند. | دستور `php artisan payments:expire-pending` و زمان‌بند پنج‌دقیقه‌ای اضافه شد. هر اجرا حداکثر ۲۰۰ سفارش قدیمی را به‌ترتیب پردازش می‌کند. |

## قابلیت‌های Barbershop که برای بدنسازی مناسب‌اند، ولی هنوز پیاده‌سازی کامل نشده‌اند

1. **پنل ورزشکار با هویت واقعی**: ثبت‌نام/ورود OTP، شماره تأییدشده، نشست قابل ابطال، سابقه خرید و برنامه‌های اختصاصی؛ به جای دادن دسترسی صرفاً براساس شماره خوداظهاری.
2. **چرخه مربیگری شخصی**: درخواست ارزیابی، پرسش‌نامه سلامت با دسترسی محدود، هدف و سابقه تمرین، برنامه دوره‌ای، پایش پیشرفت، فایل و پیام خصوصی؛ بدون کپی‌کردن تقویم صندلی/آرایشگر.
3. **درخواست و رزرو جلسه مشاوره**: ظرفیت تقویم مربی، جلوگیری از دو رزرو همزمان، وضعیت جلسه و یادآوری؛ مستقل از مفهوم رزرو صندلی Barbershop.
4. **پیامک وضعیت سفارش و ورود**: اتصال واقعی به ارائه‌دهنده پیامک، OTP با TTL و محدودیت تلاش، صف خروجی idempotent، و وضعیت نامعلوم ارسال؛ بدون نمایش کد در API عمومی.
5. **احراز هویت تکمیلی مالک**: TOTP و بازیابی امن، مدیریت نشست‌ها و تاریخچه فعالیت‌های حساس؛ مدل User فیلدهای TOTP دارد اما در این بسته نه migration و نه جریان UI/سرویس کامل TOTP موجود است.
6. **تست یکپارچه پرداخت و ذخیره‌سازی**: بانک sandbox واقعی، چند فراخوانی هم‌زمان، انقضای واقعی، بازیابی backup روی دیتابیس جداگانه و تست مرورگر موبایل.

### چه چیزهایی عمداً منتقل نشده‌اند؟

سیستم اشتراک‌فروشی آرایشگرها، اکانت سوپرادمین SaaS، مسیر QR سالن، مدیریت آرایشگر/صندلی، و کدهای Node.js/PostgreSQL. این‌ها با مدل یک مربی مستقل یکسان نیستند و انتقالشان پیچیدگی و ریسک بی‌مورد دارد.

## آزمون‌های اجراشده در همین محیط

| بررسی | نتیجه |
|---|---|
| باز کردن و بررسی دو آرشیو ZIP | انجام شد؛ هر دو مستقل بررسی شدند |
| `php -l` روی ۶۷ فایل PHP اختصاصی پروژه (app/config/routes/migrations/tests) | PASS |
| `php artisan route:list --path=api` | PASS: ۴۱ مسیر API |
| `php artisan schedule:list` | PASS: زمان‌بند پنج دقیقه‌ای ثبت شد |
| اجرای دستور انقضا پیش از نصب | PASS: بدون دسترسی به دیتابیس، به‌صورت امن اجرا نشد |
| تست بدون دیتابیس `tests/static_runtime_regressions.php` | PASS: چهار سناریو، شامل رسید نامعتبر و تطبیق درخواست idempotency |
| تست‌های Feature جدید (عدم لغو جعلی، استرداد، رسید، UUID) | به سورس تست‌ها افزوده شد؛ **در این محیط اجرا نشد** |
| تست اصلی `php tests/smoke.php` | **BLOCKED:** در PHP محیط فعلی `pdo_sqlite` نصب نیست (`could not find driver`) |
| اجرای PHPUnit | **BLOCKED:** در بسته Production وابستگی‌های توسعه/PhpUnit موجود نیست |
| MySQL/MariaDB واقعی، بانک واقعی و تست مرورگر | **در این محیط انجام نشد** |

> نبود خطای syntax یا پاس شدن آزمون بدون دیتابیس، به‌معنای تأیید صحت قطعی callback مالی یا آمادگی Production نیست.

## موارد لازم پیش از استقرار عملیاتی

- سورس **اصلی فرانت‌اند** را دریافت کنید: فایل ارسال‌شده فقط `public_html/assets/*.js` و CSSهای کامپایل‌شده را دارد و سورس React/TypeScript و فایل‌های Vite یا `package.json` در ریشه تحویل نیست. بدون سورس، افزودن امن پنل ورزشکار و بهبود بنیادی UI نباید در باندل minify شده انجام شود.
- در محیط استیج با **PHP 8.3+ و افزونه‌های لازم (pdo_mysql، curl، mbstring، gd، xml)** و MariaDB/MySQL مجزا نصب کنید، migrationها و تست‌های Feature را اجرا کنید.
- اعتبارسنجی سرور به سرور درگاه‌های زرین‌پال و SEP را با حساب تست معتبر و سناریوهای Callback منفی، مثبت، تکراری، دیرهنگام و بدون receipt انجام دهید؛ حساب بانکی واقعی فقط بعد از تأیید استیج فعال شود.
- **Cron** روی cPanel: یک بار در دقیقه `php /home/CPANEL_USER/laravel_core/artisan schedule:run` را اجرا کنید؛ مسیر واقعی PHP و HOME بسته به میزبان متفاوت است. بدون Cron انقضای زمان‌بندی‌شده خودکار نمی‌شود.
- مسیر `laravel_core` باید خارج از DocumentRoot باشد؛ رمز و کلیدهای بانک در `.env` واقعی و خارج از `public_html` ذخیره شوند و `APP_DEBUG=false`, `APP_ENV=production`, `PAYMENT_SANDBOX=false`, `SESSION_SECURE_COOKIE=true` تنظیم باشند.
- بکاپ و **بازیابی واقعی در دیتابیس جداگانه** را آزمایش کنید؛ اصلاحات این بسته سازوکار امضای بکاپ نسخه `2.2.0` را تغییر نداده‌اند تا سازگاری بکاپ موجود حفظ شود.
- سطوح دسترسی داده‌های شخصی ورزشکار را قبل از پیاده‌سازی فرم ارزیابی سلامت تعریف کنید؛ از انتشار فرم‌ها یا داده‌های سلامت در پاسخ bootstrap عمومی خودداری کنید.
