# ARASH Fitness 2.3.0 — توسعه مستقل با الهام از Barbershop (10 Nov 2026)

> **وضعیت: نسخه توسعه‌یافته برای آزمایش روی Staging — نه تأییدشده برای مشتری واقعی.**
>
> پروژه پایه دست‌نخورده از نظر معماری باقی مانده است: Laravel 13 + PHP 8.3+ + MySQL/MariaDB؛ بسته شامل `laravel_core` (خارج از ریشه عمومی) و `public_html` است. هیچ کد Node/PostgreSQL از Barbershop وارد نشده است.

## 2. چگونه صفحات جدید را تست کنیم؟

- **مدیر:** پس از ورود به `/admin`، مسیر `/coach/schedule` را باز کنید. از لینک داخل `/coach/athletes` نیز قابل دسترسی است. زمان آزاد ثبت کنید، درخواست رزرو ورزشکار را تأیید کنید و پیامی برای او بفرستید.
- **ورزشکار:** به `/athlete` بروید. اگر حساب قبلاً توسط مربی ایجاد شده، شماره را با پیامک تأیید کنید؛ سپس برای یک زمان آزاد درخواست جلسه ثبت کنید، سابقه را مشاهده کنید و پیام بفرستید.
- **فرم عمومی:** درخواست `/api/v1/consultations` همچنان برقرار است. مدیر اکنون می‌تواند همه درخواست‌ها را در بخش «درخواست‌های مشاوره از سایت» پیگیری کند.
- **پیامک تأیید:** پس از تأیید درخواست، برای هر گیرنده یک ردیف یکتا در `coach_sms_outbox` ساخته می‌شود؛ Cron آن را پردازش می‌کند. بدون پیکربندی SMS، صف منتظر می‌ماند.

## 3. ارتقای cPanel (نصب قبلی)

1. از کل `laravel_core`، `public_html` و **MySQL** در یک فضای رمزگذاری‌شده **بکاپ مستقل** بگیرید. بکاپ API سابق شامل داده‌های مربیگری نبود؛ برای ارتقای واقعی حتماً از دیتابیس خام هم بکاپ بگیرید.
2. **فایل `.env` و `storage/` موجود را حذف یا جایگزین نکنید.** از نسخه قبلی `public_html` و `laravel_core` بکاپ داشته باشید. فایل‌های کد نسخه جدید را با حفظ تنظیمات، فایل‌های خصوصی و فایل‌های رسانه منتقل کنید. پوشه `laravel_core` حتماً بیرون DocumentRoot باشد.
3. PHP 8.3+ با `pdo_mysql`, `curl`, `mbstring`, `xml`, `gd`, `openssl`, `fileinfo` و MySQL 8 / MariaDB 10.6+ لازم است. `.env` باید خارج از `public_html` بماند؛ `APP_DEBUG=false` و `SESSION_SECURE_COOKIE=true` لازم‌اند.
4. در Terminal ریشه `laravel_core`:

```bash
php artisan down
php artisan migrate --force
php artisan optimize:clear
php artisan route:list
php artisan schedule:list
php artisan up
```

5. در **cPanel > Cron Jobs** یک اجرای `schedule:run` در هر دقیقه داشته باشید:

```bash
* * * * * /usr/local/bin/php /home/USERNAME/laravel_core/artisan schedule:run >> /home/USERNAME/fitness-cron.log 2>&1
```

   مسیر PHP و `USERNAME` را مطابق هاست اصلاح کنید. دو وظیفه `payments:expire-pending` و `coaching:send-booking-sms` هر پنج دقیقه برنامه‌ریزی شده‌اند. بدون Cron اعلان‌های صف اجرا نمی‌شوند.
6. پس از بازشدن سایت، مسیرهای `/athlete`, `/athlete/register`, `/coach/athletes`, `/coach/schedule`, `/shop` و `/admin` را در موبایل و دسکتاپ تست کنید.
7. در استیج، دو درخواست هم‌زمان برای یک اسلات، تغییر نقش، CSRF، انقضای OTP، callback پرداخت، بازیابی بکاپ و رمزگذاری/HTTPS را تست کنید.

## 4. تنظیمات SMS — الگوهای ملی پیامک

در `laravel_core/.env`، بدون وارد کردن کلیدها در فایل ZIP یا GitHub:

```env
ATHLETE_MELIPAYAMAK_TOKEN=
ATHLETE_MELIPAYAMAK_BODY_ID=
BOOKING_MELIPAYAMAK_TOKEN=
BOOKING_MELIPAYAMAK_BODY_ID=
COACH_NOTIFICATION_PHONE=
FITNESS_REQUIRE_VERIFIED_CHECKOUT=false
```

- الگوی OTP باید **دقیقاً یک متغیر** داشته باشد: `[code]`.
- الگوی تأیید جلسه باید **سه متغیر با ترتیب دقیق** `[AF-bookingId, YYYY/MM/DD, HH:mm]` داشته باشد. این ساختار باید در پنل ارائه‌دهنده تأیید شود؛ شناسه قالب‌ها ساختگی نیستند و باید از سرویس واقعی دریافت شوند.
- `BOOKING_MELIPAYAMAK_TOKEN` با کلید واقعی سمت سرور تنظیم شود. اطمینان حاصل کنید endpoint `console.melipayamak.com/api/send/shared/...` با خروجی عددی `recId` در حساب واقعی شما سازگار است؛ این سازگاری **تست واقعی نشده**.
- نتیجه `unknown`: ممکن است پیامک ارسال شده باشد؛ **ارسال مجدد خودکار عمداً ممنوع است**. از پنل خدماتی provider وضعیت را بررسی کنید.
- بعد از تغییر `.env`: `php artisan config:clear && php artisan config:cache` (اگر config cache فعال است).

## 5. سیاست نشست، حریم خصوصی و خرید

- نقش `admin` و `athlete` مستقل بررسی می‌شوند. مسیرهای خصوصی حتماً احراز هویت، CSRF برای درخواست‌های تغییر‌دهنده و `Cache-Control: no-store` دارند.
- شماره خوداظهاری‌شده صرفاً برای دسترسی به خرید و رزرو کافی نیست. تأیید OTP تاریخ‌دار (`phone_verified_at`) لازم است.
- رمز عبور اولیه حساب‌های دستی، تا زمان بازطراحی احراز هویت و بازیابی حساب، باید با کانال امن تحویل شود. **پنل مربی هنوز TOTP/Google login کامل ندارد**.
- پیام‌های خصوصی ممکن است اطلاعات حساس ورزشکار را دربرگیرند. فقط کاربران مجاز باید به آن دسترسی داشته باشند؛ پیش از بهره‌برداری واقعی، سیاست حذف، نگهداری و رضایت کاربر را تکمیل کنید.

## 6. بکاپ و سازگاری نسخه‌ها

- `RELEASE_VERSION=2.3.0`؛ قالب امضای JSON برای سازگاری باقی مانده: `white-label-fitness-backup-v2.2.0`.
- بکاپ‌های **همین نصب** با امضای HMAC قابل بازگردانی هستند؛ برای بازیابی در نصب تازه با APP_KEY جدید، تغییر کلید امضا مشکل‌ساز می‌شود.
- بکاپ JSON اکنون شامل نام، شماره موبایل، پیام‌ها، سفارش‌ها و **هش رمزهای عبور** است و **رمزگذاری‌شده نیست**. فقط در حافظه رمزگذاری‌شده نگهداری کنید، در فضای عمومی یا ایمیل بدون رمزگذاری قرار ندهید.
- احراز هویت‌های جاری (`sessions`) و چالش‌های موقت OTP در بکاپ ذخیره نمی‌شوند. صف پیامک restore‌شده که قبلاً `queued/sending` بوده به `unknown` می‌رود تا تکرار ناخواسته SMS رخ ندهد.
- بازیابی فایل‌ها و دیتابیس همچنان باید **در یک دیتابیس آزمایشی جداگانه** تست شود. عملیات فایل‌های storage با transaction دیتابیس کاملاً اتمیک نیست و یک ریسک شناخته‌شده است.

## 7. محدودیت‌هایی که نباید پنهان شوند

- این بسته فقط **فایل‌های کامپایل‌شده React** را دارد، نه سورس TSX/Vite اصلی. برای بازطراحی حرفه‌ای کلی سایت، پوشه سورس لازم است؛ در باندل minified دستکاری نکرده‌ایم.
- PHP CLI محیط این بازبینی فاقد `pdo_mysql`, `pdo_sqlite` و برخی افزونه‌های لازم است؛ آزمون یکپارچه MySQL و PHPUnit اجرا نشد. آزمون‌های Feature نوشته شده‌اند و باید در محیط دارای PHP Extensions اجرا شوند.
- **درگاه واقعی زرین‌پال/SEP، SMS واقعی، UX مرورگر موبایل، هم‌زمانی MySQL و restore دیتابیس مجزا** هنوز با نتیجه واقعی تأیید نشده‌اند.
- فرآیند فروش خودکار اشتراک مربیگری، تولید خودکار برنامه تمرین/تغذیه، OAuth/TOTP مالک، اشتراک‌گذاری فایل خصوصی، PWA و داشبورد مالی پیشرفته هنوز پیاده‌سازی نشده‌اند.
- نسخه فعلی برای **Staging** مناسب است؛ عبارت Production-ready قبل از تست مستقل واقعی صحیح نیست.
